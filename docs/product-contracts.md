# عقود المنتج | Product Contracts

الإصدار: MVP v1. هذه العقود هي حدود سلوكية لا يجوز للواجهة أو نموذج ذكاء
اصطناعي تجاوزها. الأسماء البرمجية بالإنجليزية ثابتة؛ النصوص المعروضة تُترجم
للعربية والإنجليزية.

## 1. الثوابت غير القابلة للتفاوض

1. **Confirmed-only generation:** لا يستخدم التوليد إلا حقائق حالتها
   `confirmed`. مجرد رفع CV لا يعد تأكيدًا.
2. **Claim provenance:** كل جملة واقعية في CV أو رسالة تقديم لها رابط واحد على
   الأقل إلى حقيقة مؤكدة تخص المستخدم. صياغة انتقالية غير واقعية تُوسم كذلك.
3. **Fail closed:** ادعاء بلا دليل، أو دليل محذوف/غير مؤكد، يجعل المستند غير
   صالح للتصدير حتى حذف الادعاء أو تأكيد الحقيقة.
4. **No inferred eligibility:** الجنسية وحق العمل والاستعداد للانتقال والتفضيلات
   تأتي من تصريح المستخدم فقط، ولا تستنتج من الاسم أو اللغة أو الموقع.
5. **Coverage, not probability:** الرقم المعروض هو تغطية متطلبات الوظيفة، وليس
   احتمال مقابلة أو قبول. الجاهزية `low|medium|high` مع ثقة وأسباب فقط.
6. **Manual submission:** المنتج يجهز الحزمة ويفتح الرابط الأصلي؛ المستخدم
   يراجع ويضغط Submit خارج النظام.
7. **No platform fetch by URL:** تخزين رابط أو نص وظيفة لا يجيز للخادم جلب
   الصفحة. البحث يتطلب feed/API مرخصًا وسياسة مصدر تسمح به.
8. **Outcome by user confirmation:** لا يُقرأ البريد ولا تستنتج النتيجة في
   الـMVP؛ المستخدم يسجلها.
9. **Concurrent trust changes fail closed:** يحتفظ الملف والوظيفة بعدّادات
   مراجعة، ويرفض الخادم بـ`409` أي تحليل أو اعتماد مستند بُني على snapshot قديم
   أو أثناء حذف البيانات.

## 2. النموذج المفاهيمي

| الكيان | الغرض والعلاقة الأساسية |
|---|---|
| `User` | هوية Clerk وlocale؛ لا يخزن كلمة مرور أو session token. |
| `CareerProfile` | حاوية حقائق المستخدم وتفضيلاته؛ يحمل `evidence_revision` وحارس بدء الحذف، وملف نشط واحد في MVP. |
| `Source` | إدخال يدوي أو CV أو LinkedIn export رفعه المستخدم أو feed مرخص. |
| `EvidenceFact` | حقيقة ذرية بقيمة منظمة، مصدر، موضع دليل، ثقة وحالة تحقق. |
| `Job` | وصف أدخله المستخدم أو سجل من feed مرخص، مع مصدر وتاريخ جلب/انتهاء و`requirements_revision`. |
| `Requirement` | شرط إلزامي أو مفضل مستخرج من وصف الوظيفة. |
| `MatchAnalysis` | ربط المتطلبات بالحقائق وحساب التغطية والقرار والجاهزية، مع revisions الأدلة والمتطلبات التي بُني عليها. |
| `Document` | CV أو cover letter بإصدار ولغة؛ يبنى محتواه في الخادم من claims محكومة ويحفظ revision الأدلة عند المراجعة. |
| `Claim` | وحدة نصية واقعية أو قالب غير واقعي مسموح؛ تخضع لقواعد التحقق أدناه. |
| `ClaimEvidence` | **منفذ:** علاقة فريدة بين claim وحقيقة مؤكدة، وتظهر في استجابة المستند. |
| `Application` | الوظيفة، نسخة CV/الرسالة، الحالة، القناة والتواريخ. |
| `Outcome` | نتيجة أكدها المستخدم مرتبطة بطلب، مع نوع المقابلة إن وجد. |
| `SourcePolicy` | الصلاحيات المستقلة للمصدر وتاريخ/مرجع مراجعة الشروط. |
| `DeletionReceipt` | **منفذ:** إيصال غير معرّف للمستخدم، يحفظ وقت الحذف وأعداد السجلات المحذوفة. |
| `AuditEvent` | **قبل الإنتاج وغير منفذ حاليًا:** سجل عام لمن غيّر حقيقة/حالة/موافقة ومتى. |

كل سجل يخص المستخدم يحمل owner مباشرًا أو يصل إلى المالك عبر الملف، ويخضع
للتفويض في الخادم. مسار الحذف الحالي يحذف رسم العلاقات المخزن في PostgreSQL
ويحتفظ بـ`DeletionReceipt` غير معرف. حذف object storage والنسخ الاحتياطية ليس
منفذًا بعد، وهو بوابة إلزامية قبل تخزين ملفات أصلية في الإنتاج.

## 3. الحالات والانتقالات

### حقيقة مهنية

- `extracted`: استخرجها النظام ولديها ثقة وموضع مصدر، لكنها لم تُراجع.
- `unconfirmed`: أنشأها أو عدلها المستخدم ولم يؤكد صحتها بعد، أو extraction
  منخفض الثقة.
- `confirmed`: أكد المستخدم القيمة الحالية صراحة؛ عند تعديلها تعود
  `unconfirmed` حتى إعادة التأكيد.

التصحيح أو سحب التأكيد يوقف استخدامها فورًا، يعيد المستندات المعتمدة عليها إلى
`draft`، ويبطل التحليلات السابقة حتى إعادة التحليل. يحتفظ التصحيح بالقيمة
المستخرجة الأصلية وسببه، لكنه لا يغني عن `AuditEvent` العام قبل الإنتاج.
يزيد التغيير `evidence_revision` ذريًا؛ وقبل حفظ تحليل أو مراجعة مستند يعيد
الخادم التحقق من revision داخل المعاملة، لذلك لا يستطيع طلب متزامن قديم إعادة
نشر مخرج مبني على دليل سُحب لاحقًا.

### قرار التقديم

| القيمة | معناها |
|---|---|
| `apply_now` | لا توجد فجوة إلزامية معروفة، والتغطية/التفضيلات تبرر الوقت. |
| `improve_then_apply` | توجد تحسينات قابلة للتنفيذ قبل الموعد دون ادعاء خبرة غير موجودة. |
| `low_return` | مانع صريح أو فجوة إلزامية كبيرة تجعل العائد المتوقع منخفضًا. |
| `need_information` | وصف أو ملف غير كافٍ؛ لا يعرض قرارًا حاسمًا. |

قرار المستخدم النهائي دائمًا. يستطيع إضافة requirement أو تصحيحه أو سحبه مع
سبب، ثم يعتمد القائمة صراحة ويعيد التحليل. لا يظهر `apply_now` قبل اعتماد قائمة
المتطلبات الحالية. تعديل الـrequirement لا يعني override يدويًا لرابط evidence؛
تُصحح الحقيقة أو المتطلب ثم تعاد المطابقة.

### جاهزية المقابلة

`low | medium | high` مع `confidence=low|medium|high` وقائمة أسباب. يمنع الحقل
الرقمي الذي يمكن تفسيره كاحتمال مقابلة في الـMVP.

### الطلب

المسار المعتاد:

```text
discovered -> saved -> preparing -> ready -> submitted -> interview -> offer
                                            |            -> rejected
                                            -> withdrawn
```

القيم الثابتة: `discovered`, `saved`, `preparing`, `ready`, `submitted`,
`interview`, `rejected`, `offer`, `withdrawn`.

- الانتقال إلى `submitted` يتطلب تأكيد المستخدم وتاريخ الإرسال؛ لا ينفذه worker.
- `interview`, `rejected`, و`offer` نتائج يضيفها المستخدم يدويًا في الـMVP.
- التصحيح الرجعي جزء من العقد المستهدف. التنفيذ الحالي يحدث السجل دون
  `AuditEvent` عام؛ لذلك يجب إضافة سجل التدقيق قبل اعتبار هذا المسار جاهزًا
  للإنتاج.
- `rejected` و`withdrawn` نهائيتان تشغيليًا؛ reopening عملية صريحة ومراجعة.

## 4. تدفقات المستخدم ومعايير القبول

### أ. تأسيس الملف

1. يختار المستخدم العربية أو الإنجليزية ويصرح بتفضيلاته والأهلية التي يريد
   مشاركتها.
2. يدخل البيانات يدويًا أو يرفع PDF/DOCX أو LinkedIn PDF/export خاصًا به.
3. تعرض الحقائق المستخرجة واحدة واحدة مع المصدر والثقة؛ يؤكد أو يصحح أو يرفض.
4. لا تعتبر جودة الملف مكتملة ما دام شرط أساسي غير معلوم أو حقائق مهمة غير مؤكدة.

القبول: شهادة أو تاريخ منخفض الثقة يبقى غير مؤكد؛ بيانات connections/messages
في LinkedIn export تُهمل؛ ولا تظهر حقيقة مرفوضة في أي مخرج.

#### عقد الاستيراد المنفذ

- `POST /v1/profiles/{profile_id}/imports` يستقبل multipart بحقل `file`، بعد
  التحقق من ملكية الملف المهني.
- الصيغ المدعومة هي CV بصيغة PDF أو DOCX، وLinkedIn data export بصيغة ZIP.
  الامتداد وMIME وتوقيع الملف يجب أن تتفق؛ الملفات المشفرة أو الحاويات غير
  الآمنة ترفض.
- الحد الافتراضي للرفع 10 MB. توجد حدود إضافية للصفحات، وعدد/حجم عناصر ZIP،
  نسبة الضغط، طول النص وعدد الحقائق؛ تجاوز حجم الرفع يعيد `413`، والمدخل غير
  المدعوم أو غير الآمن يعيد `422`.
- LinkedIn ZIP يقرأ فقط `Profile`, `Positions`, `Education`, `Certifications`,
  `Skills`, `Languages` و`Projects` بصيغة CSV، ويتجاهل Connections وMessages
  وباقي بيانات الأشخاص الآخرين.
- الملف الخام يحلل في الذاكرة ولا يحتفظ به التنفيذ الحالي. يحفظ المصدر hash
  وحجمًا وإصدار parser وعدد المرشحات، وتعود كل الحقائق بحالة `extracted` مع
  `requires_user_review=true`.
- Endpoints التأكيد والتصحيح وسحب التأكيد منفذة. تعديل الحقيقة يعيدها
  `unconfirmed`، يحفظ الأصل والسبب، ويبطل التحليلات والمراجعات المشتقة. واجهة
  هذا التدفق متصلة؛ يبقى سجل `AuditEvent` العام واختبار تزامن PostgreSQL من
  بوابات beta.

### ب. إضافة وتحليل وظيفة

1. يلصق المستخدم الوصف والرابط اختياريًا، أو يختار وظيفة من feed مرخص.
2. يستخرج النظام الإلزامي والمفضل والخبرة والمهارات والتعليم واللغة والموقع
   والأهلية المذكورة صراحة.
3. لكل requirement حالة `covered|missing|unknown` وروابط الأدلة والتفسير.
4. يضيف المستخدم المتطلبات التي سقطت، يصحح أو يسحب false positives، ثم يعتمد
   القائمة الحالية.
5. تعرض أوزان ومكونات التغطية، قرار التقديم، الجاهزية والثقة؛ قبل الاعتماد تكون
   النتيجة `need_information` مهما كانت التغطية الأولية.

القبول: شرط شهادة غير موجود يظهر كفجوة إلزامية ولا يختفي داخل المتوسط؛ الوصف
الغامض يعيد `need_information`؛ الرابط وحده لا يؤدي إلى fetch.

### ج. تخصيص المستند

1. يختار المستخدم job، النوع، اللغة، والنسخة الأساسية.
2. يستخدم النظام confirmed fact IDs فقط ويولد صياغة ATS آمنة.
3. تعرض الواجهة diff ومصدر كل تعديل وتحذيرات validator.
4. لا يتاح export حتى نجاح validation وموافقة المستخدم.

القبول: إنجاز بلا رقم يبقى بلا رقم؛ النسختان العربية والإنجليزية تعكسان الحقائق
نفسها؛ حذف حقيقة يجعل المستند المعتمد عليها غير صالح حتى التجديد.

#### عقد claims المحافظ والمنفذ

الـclaim هي وحدة الثقة الوحيدة التي يبني منها الخادم محتوى المستند. حقل
`content` القادم من العميل لا يعتمد كمصدر مستقل؛ الخادم يعيد تركيب المحتوى من
claims المقبولة بالترتيب.

- الـclaims الواقعية (`identity`, `experience`, `education`, `skill`,
  `achievement`, `project`, `certification`, `language`, `preference`) تحتاج
  `ClaimEvidence` إلى حقيقة واحدة أو أكثر من الملف نفسه وحالتها `confirmed`.
- نوع الحقيقة يجب أن يدعم نوع claim. مثلًا skill قد يدعمها skill أو experience
  أو project أو certification، بينما education لا يدعمها إلا education.
- كل رقم في claim يجب أن يظهر في الدليل. لا يجوز إدخال نسبة أو مدة أو أثر كمي
  جديد.
- يجب أن تتطابق الكلمات المادية للـclaim ذريًا مع قطعة دليل مؤكدة واحدة؛ لا
  يتجاهل الفحص إلا أدوات التعريف الإنجليزية والترقيم. لا يجوز حذف نفي أو فاعل أو
  حرف جر دلالي، ولا جمع كلمات من حقائق متفرقة لصناعة علاقة غير موجودة.
- النصوص غير الواقعية محصورة في `salutation`, `intent`, `transition`، بلا روابط
  أدلة وبمطابقة قالب ثابت يملكه الخادم. لا يستطيع العميل تسمية ادعاء مهني
  `transition` لتجاوز الفحص.
- أي claim بلا دليل، من ملف آخر، بحالة غير مؤكدة، بفئة غير مناسبة، برقم جديد،
  أو بصياغة غير مؤصلة يعيد `422` مع الرمز `unsupported_claims` ولا ينشئ المستند.
- `POST /v1/documents/{id}/validate` يعيد التحقق من الحالة الحالية للأدلة.
  ينشأ كل مستند `draft`، ويصبح `export_ready` فقط عبر انتقال مراجعة خادمي يسجل
  المراجع والوقت وhash سطح المراجعة. `export_allowed=true` يتطلب أدلة سليمة
  ومراجعة حالية و`evidence_revision_at_review` مطابقًا؛ تغيير حقيقة يعيد
  المستند تلقائيًا إلى `draft`، وCAS يمنع اعتماد snapshot متزامن قديم.

### د. التقديم والتتبع

1. ينشئ النظام حزمة CV/رسالة قابلة للتنزيل أو النسخ.
2. يفتح المستخدم الرابط الأصلي ويقدم يدويًا.
3. يؤكد الإرسال ثم يحدث الحالة والنتائج لاحقًا.
4. تعرض اللوحة أفضل الفرص والإجراءات والمتابعات والقمع، لا حافز زيادة العدد.

القبول: لا endpoint يضغط Submit أو يخزن cookies؛ كل `submitted` له تأكيد بشري؛
المقابلة المؤهلة تستبعد الرد الآلي واختبار الفرز غير البشري.

## 5. عقد HTTP v1

Base path هو `/v1`. في الإنتاج، كل مسارات v1 تتطلب `Authorization: Bearer
<Clerk JWT>`؛ health endpoints عامة ولا تعيد بيانات أو تفاصيل اعتماديات حساسة.
الملكية تستخرج من JWT لا من مدخل العميل. JSON UTF-8، والتواريخ ISO 8601 UTC،
والقيم enum البرمجية لا تُترجم.

| Method | Path | السلوك |
|---|---|---|
| `GET` | `/health/live` | العملية تعمل؛ بلا فحص اعتماديات. |
| `GET` | `/health/ready` | الخدمة مستعدة والاعتماديات الحرجة متاحة. |
| `POST/GET/PATCH` | `/v1/profiles` | إنشاء/قراءة/تعديل الملف المملوك للمستخدم. |
| `GET` | `/v1/profiles/{id}/summary` | جودة الملف وعدّادات المراجعة وفق التعريف نفسه المستخدم في Dashboard. |
| `POST/GET` | `/v1/profiles/{id}/sources` | إضافة مصدر يدوي وقراءته؛ أنواع upload/feed ينشئها الخادم فقط. |
| `POST` | `/v1/profiles/{id}/imports` | تحليل PDF/DOCX/LinkedIn ZIP وإرجاع حقائق `extracted` للمراجعة؛ يرفض الناتج الفارغ والملف المكرر. |
| `POST/GET` | `/v1/profiles/{id}/facts` | إضافة/عرض حقائق الملف. |
| `POST` | `/v1/profiles/{id}/facts/{fact_id}/confirm` | تأكيد القيمة الحالية صراحة. |
| `PATCH` | `/v1/profiles/{id}/facts/{fact_id}` | تصحيح حقيقة مع سبب؛ تعود `unconfirmed` ويحفظ الأصل. |
| `POST` | `/v1/profiles/{id}/facts/{fact_id}/unconfirm` | سحب التأكيد وإبطال المخرجات المشتقة. |
| `GET` | `/v1/source-policies` | عرض قدرات المصادر وتاريخ مراجعتها. |
| `POST` | `/v1/jobs/manual` | إنشاء وظيفة من النص؛ URL metadata فقط. |
| `GET` | `/v1/jobs` | قائمة وظائف المستخدم الحالية؛ filtering/pagination لم ينفذا بعد. |
| `GET` | `/v1/jobs/{id}` | وظيفة مملوكة مع وصفها ومصدرها. |
| `POST` | `/v1/jobs/{id}/requirements` | إضافة متطلب أسقطه المستخرج مع سبب. |
| `PATCH` | `/v1/jobs/{id}/requirements/{requirement_id}` | تصحيح متطلب وإبطال التحليل القديم. |
| `POST` | `/v1/jobs/{id}/requirements/{requirement_id}/retire` | سحب false positive مع سبب دون محو أصله. |
| `POST` | `/v1/jobs/{id}/requirements/review` | اعتماد قائمة المتطلبات الحالية وتثبيت hash لها. |
| `POST` | `/v1/jobs/{id}/analyze` | تحليل المتطلبات والتغطية والقرار. |
| `GET` | `/v1/jobs/{id}/analyses/latest` | آخر تحليل حالي غير مبطل ومملوك للمستخدم. |
| `POST/GET` | `/v1/documents` | إنشاء/عرض نسخ CV ورسائل التقديم. |
| `GET` | `/v1/documents/{id}` | مستند مع claims وروابط provenance؛ الفحص عبر endpoint مستقل. |
| `POST` | `/v1/documents/{id}/validate` | فحص confirmed-only؛ الفشل يمنع التصدير. |
| `POST` | `/v1/documents/{id}/review` | مراجعة بشرية خادمية؛ تثبت hash وتحوّل إلى `export_ready`. |
| `POST/GET` | `/v1/applications` | إنشاء/عرض طلبات المستخدم. |
| `PATCH` | `/v1/applications/{id}` | تحديث الحالة/الملاحظات؛ `AuditEvent` العام مطلوب قبل الإنتاج. |
| `POST` | `/v1/applications/{id}/outcomes` | تسجيل نتيجة مؤكدة من المستخدم. |
| `GET` | `/v1/dashboard` | ملخص الإجراءات والجودة والقمع للمستخدم. |
| `GET` | `/v1/me/export` | تنزيل JSON مملوك للمستخدم يشمل الملف والأدلة والوظائف والمخرجات والطلبات. |
| `DELETE` | `/v1/me/data` | حذف رسم بيانات المستخدم وإرجاع `DeletionReceipt` غير معرف. |

### عقد التصدير والحذف المنفذ

- `GET /v1/me/export` يعيد JSON attachment يحوي `schema_version` ووقت الإنشاء،
  ثم الملف والمصادر والحقائق والوظائف والتحليلات والمستندات مع ClaimEvidence
  والطلبات مع نتائجها. الاستعلام owner-scoped ولا يعيد بيانات مستخدم آخر.
- التصدير متاح أيضًا قبل onboarding؛ عندها يكون `profile=null` والقوائم فارغة.
- `DELETE /v1/me/data` يحذف بترتيب صريح كل السجلات المملوكة في PostgreSQL، ولا
  يحذف `SourcePolicy` المشترك. يثبت `deletion_started_at` أولًا، ثم ترفض حراس
  mutation أي كتابة متأخرة داخل الرسم الجاري حذفه. يعمل أيضًا للحساب الذي لم
  ينشئ ملفًا.
- الاستجابة تحتوي معرف إيصال ووقت الإكمال وأعدادًا حسب نوع السجل، ولا تحتوي
  معرف المستخدم أو محتواه. يبقى `DeletionReceipt` كإثبات تقني غير معرف.
- التنفيذ الحالي لا يحتفظ بملف الاستيراد الخام. عند إضافة object storage أو
  نسخ احتياطية، يجب توسيع مسار الحذف واختباره قبل الإنتاج.

العمليات المكلفة يمكن أن تتحول إلى `202 Accepted` مع `operation_id` دون تغيير
معنى الطلب. عند ذلك تكون حالات العملية `queued|running|succeeded|failed|cancelled`
والـresource الناتج يظل في PostgreSQL. حتى إضافة endpoint موحد للعمليات، التنفيذ
الحتمي الحالي يعيد النتيجة synchronously.

### أخطاء الحدود

- `400`: مدخل غير صالح دلاليًا، مثل URL بلا وصف عندما لا يسمح المصدر بالجلب.
- `401/403`: JWT مفقود/غير صالح أو سجل لا يملكه المستخدم. لا تكشف استجابة 403
  وجود سجل لمستخدم آخر.
- `404`: المورد غير موجود ضمن نطاق المستخدم.
- `409`: تعارض حالة أو idempotency أو محاولة تأكيد قيمة تغيرت.
- `422`: validation بنيوي؛ التفاصيل لا تتضمن محتوى ملف حساس.
- `429`: عقد مستهدف قبل الإنتاج عند إضافة rate limiting مع `Retry-After`؛ ليس
  منفذًا في foundation الحالي.
- `503`: اعتماد مؤقت غير متاح؛ لا يسقط العمل بصمت.

قبل beta يجب أن يحمل كل رد خطأ `request_id` ورمزًا ثابتًا ورسالة قابلة للترجمة؛
هذا الغلاف الموحد غير منفذ بعد في الـfoundation الحالي. لا تعاد stack traces
أو prompt أو نص CV في الإنتاج.

## 6. عقد نسبة تغطية المتطلبات

1. يقسم التحليل المتطلبات إلى mandatory وpreferred ويعرض وزن كل عنصر.
2. مساهمة `covered` واضحة، `missing` صفر، و`unknown` لا يُعرض كأنه missing؛ يظهر
   مقدار عدم اليقين منفصلًا.
3. أي مانع mandatory صريح يظهر مستقلًا مهما كانت الدرجة الإجمالية.
4. التعليم واللغة والأهلية لا تستنتج من مهارة مشابهة.
5. تحفظ نسخة algorithm/ontology مع التحليل لإعادة الإنتاج والمقارنة.

لا يوجد threshold سري يضمن نتيجة. تغيير الأوزان يحتاج fixture regression
بالعربية والإنجليزية ومراجعة انحياز قبل النشر.

## 7. عقد سياسة المصدر

كل مصدر يملك على الأقل: `source_key`, `intake_method`, `permission_basis`,
`terms_reviewed_at`, `can_search_automatically`, `can_fetch_details`,
`can_apply_automatically` و`active`. كل قدرات الأتمتة `false` افتراضيًا. غياب
سجل أو انتهاء المراجعة يغلق القدرة ولا يفتحها.

الإدخال اليدوي وملف المستخدم يسمحان بالمعالجة التي طلبها المستخدم، لكنهما لا
يمنحان حق إعادة نشر بيانات منصة أو جلب رابطها. `can_apply_automatically` يبقى
`false` في الـMVP لكل المصادر دون استثناء.

## 8. Definition of Done

- اختبارات backend تغطي confirmed-only، المصدر المقفول، ownership، enums، وحالة
  الوصف الغامض.
- اختبارات frontend تغطي RTL/LTR، keyboard focus، النص غير العددي للجاهزية،
  ووضوح أن التقديم يدوي.
- OpenAPI وTypeScript types متسقان أو يكشف CI الانحراف.
- لا أسرار أو بيانات شخصية في fixtures/logs/snapshots.
- migration لها مسار upgrade واختبار على قاعدة فارغة.
- أي تكامل خارجي جديد يجتاز checklist السياسة والخصوصية قبل تفعيل feature flag.
